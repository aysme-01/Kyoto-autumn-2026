# 秋の京都｜JSONデータ設計 ver.1.0（検討稿）

## 01. 基本方針

### ファイル構成

- JSONファイルは `trip.json` の1ファイルとする。
- ファイルのルートに `schemaVersion` を持たせる。
- スキーマの初期バージョンは `1` とする。

### 命名規則・ID管理

- 項目名は lowerCamelCase で統一する。
- IDは文字列型とし、kebab-case で統一する。
- IDは同一テーブル内で一意とする。
- 名称や表示順の変更に伴うIDの変更は行わない。
- テーブル間の関連付けはIDによって行う。
- 区分値は固定の英語コードで管理する。

### データ形式

- 日付は YYYY-MM-DD 形式とする。
- 時刻は HH:mm 形式とする。
- タイムゾーンは Asia/Tokyo とする。
- 所要時間は分単位の数値型とする。
- 金額は円単位の数値型とする。

### 未設定値

- 単一の任意項目の未設定値は `null` とする。
- 配列の未設定値は空配列 `[]` とする。
- 真偽値は `true` または `false` とする。
- 金額が無料の場合は `0`、不明の場合は `null` とする。

### 移動情報

- 移動区間は乗降・移動手段の変更単位で分割する。
- 途中の停車駅や乗降を伴わない直通運転では分割しない。
- 時刻表は移動区間の子要素として管理する。
- 乗車予定時刻と時刻表は別項目として管理する。

### スケジュール管理方針

- 通常予定と移動予定は同一テーブルで管理する。
- 予定種別は type で管理する。
- 予定種別に応じて画面の描画方法を切り替える。
- 全体の予定順序は schedules.sortOrder で管理する。
- 移動区間の順序は routes.sortOrder で管理する。
- sortOrder は整数型とし、初期登録時は10刻みで採番する。
- 同一の順序管理範囲内で sortOrder の重複を許可しない。

## 03. テーブル関連

| 親テーブル | 子テーブル | 関連 | 関連付け方法 |
| --- | --- | --- | --- |
| trip | schedules | 1対多 | 同一JSON内で管理 |
| spots | schedules | 多対多 | schedules.spotIds(任意) |
| schedules | routes | 1対多 | routes.scheduleId（必須） |
| schedules | reservations | 1対多 | reservations.scheduleId（任意） |
| spots | reservations | 1対多 | reservations.spotId（任意） |
| spots | menus | 1対多 | 入れ子構造 |
| routes | timetable | 1対多 | 入れ子構造 |
| — | notes | なし | 独立管理 |

### 関連付けの方針

- 旅行基本情報は1件のみとする。
- 各テーブルに tripId は持たせない。
- スポットを参照しないスケジュールの spotId は null とする。
- 移動区間は移動種別のスケジュールに紐づける。
- 移動区間の表示順は、同一 scheduleId 内の sortOrder の昇順とする。
- メニューはスポットの子要素として管理する。
- 時刻表は移動区間の子要素として管理する。
- 入れ子構造の子要素は、親への参照IDを持たない。
- メモは独立したデータとして管理する。
- 予約情報は独立したデータとして管理する。
- 予約情報とスケジュールの関連付けは任意とする。
- スケジュールに紐づかない予約情報の scheduleId は null とする。
- 予約情報とスポットの関連付けは任意とする。
- スポットに紐づかない予約情報の spotId は null とする。
- 予約情報とスケジュールの参照先スポットに矛盾がないこと。

### 予約情報の参照方針

- 共通ヘッダーの予約リストから全予約情報を参照できる。
- スケジュールに紐づく予約情報は、該当するスケジュールからも参照できる。
- いずれの画面からも同一の予約情報を参照する。

#### 管理方針

- スポットはスケジュールとは独立して管理する。
- スケジュールに紐づかないスポットの登録も可能とする。
- 1つのスポットに対して種別を1つ設定する。
- 営業時間は通常営業・夜間営業などの区分ごとに管理する。
- 営業時間は旅行日当日の情報を登録する。
- 料金は大人1名分の金額を基本とする。
- 料金区分は複数登録可能とする。
- 無料の場合は金額を 0、不明の場合は null とする。
- 推奨滞在時間はスケジュール上の所要時間とは別に管理する。
- 緯度・経度を設定する場合は両方を設定する。
- その他の写真・見どころ・メニューの表示順は配列順とする。
- 配列項目に登録内容がない場合は空配列とする。
- 未登録の情報は画面上に表示しない。
- 営業時間・料金・見どころ・メニューは独立したテーブルとせず、スポットの子要素として管理する。

#### 訪問区分の判定方針

- スポットは「行くスポット」と「候補スポット」に分類して表示する。
- いずれかの schedules.spotIds に含まれるスポットを「行くスポット」とする。
- どの schedules.spotIds にも含まれないスポットを「候補スポット」とする。
- 訪問区分はスケジュールとの関連付けを基にJSで判定する。
- 訪問区分をデータとして保持しない。

#### 管理方針

- 移動区間は移動種別のスケジュールに紐づける。
- 1つの移動スケジュールに複数の移動区間を登録可能とする。
- 移動区間は乗降・移動手段の変更単位で分割する。
- 途中の停車駅や乗降を伴わない直通運転では分割しない。
- 表示順は同一 scheduleId 内の sortOrder の昇順とする。
- sortOrder は整数型とし、初期登録時は10刻みとする。
- 移動区間の所要時間は分単位で保持する。
- 乗り換え等の待ち時間は独立したデータとして保持しない。
- 移動区間の所要時間の合計とスケジュール全体の所要時間は必ずしも一致しない。
- 関連リンクは公式時刻表・駅構内図・運行情報など、用途に応じて複数登録可能とする。
- 関連リンクの表示順は配列順とする。
- 未設定の任意項目は null とする。
- 配列項目に登録内容がない場合は空配列とする。

#### 時刻表の管理方針

- 時刻表は移動区間の子要素として管理する。
- 旅行日当日のダイヤを登録する。
- 乗車予定時刻を中心に、前後の便を登録する。
- 登録する時間帯および便数に制限は設けない。
- 予定の前倒しや遅延を考慮し、余裕を持った時間帯の登録を推奨する。
- 表示順は出発時刻の昇順とする。
- 乗車予定時刻と時刻表は別項目として管理する。
- 行先・方面および乗り場が未設定の場合は親の移動区間の情報を使用する。
- 時刻表が未登録の場合は空配列とする。
- 外部の時刻表へのリンクは links で管理する。

#### 時刻表の表示方針

- 時刻表が登録されている場合のみモーダル表示ボタンを表示する。
- 乗車予定時刻と一致する便を強調表示する。
- 旅行日当日は現在時刻より前の便をグレーアウトする。
- 旅行日当日は現在時刻以降の最も早い便を「次の便」として表示する。
- モーダル表示時は乗車予定便付近まで自動スクロールする。
- 登録済みの全便を閲覧可能とする。
